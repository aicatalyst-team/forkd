# PoC Plan: forkd\n\n## Project Classification\n- **Type:** infrastructure\n- **Key Technologies:** Rust, Firecracker microVMs, KVM, userfaultfd, copy-on-write memory, Axum (HTTP), Linux cgroups/namespaces\n- **ODH Relevance:** forkd enables rapid, hardware-isolated microVM sandboxing for AI agent fan-out — a core capability for safely running untrusted AI agent code at scale. On OpenShift AI / ODH, it could complement workbench environments by providing sub-200ms sandbox forking for agent-based workloads, enabling parallel exploration (\"branch a thinking agent\") with full KVM isolation.\n\n## PoC Objectives\nWhat we want to prove:\n1. The forkd-controller daemon builds into a container image and starts successfully, binding its HTTP API on port 8889.\n2. The controller's HTTP API responds to basic status and listing endpoints (GET /v1/sandboxes, GET /v1/snapshots) without requiring KVM or Firecracker on the host.\n3. The controller handles invalid requests gracefully (proper error codes/messages).\n4. The container image is small, secure (non-root by default), and follows the existing Dockerfile conventions.\n\n**Scope limitation:** forkd's core value (forking microVMs via KVM + userfaultfd) requires a bare-metal or nested-virt host with `/dev/kvm` access and the `--privileged` flag. A Kubernetes PoC cluster typically does not expose KVM to pods. Therefore, this PoC validates that the **controller daemon** (the HTTP management plane) builds, starts, and serves its API correctly — proving the containerization and deployment pipeline works. Full microVM forking would require a KVM-enabled node pool, which is documented as a follow-up.\n\n## Infrastructure Requirements\n- **Inference Server:** none\n- **Vector Database:** none\n- **Embedding Model:** none\n- **GPU Required:** no\n- **Persistent Storage:** none (the controller can run stateless for PoC; production needs /var/lib/forkd)\n- **Resource Profile:** small (the controller daemon is a lightweight Rust binary)\n- **Sidecar Containers:** none\n\n## Test Scenarios\n\n### Scenario 1: health-check\n- **Description:** Verify the forkd-controller HTTP server is running and accepting connections on port 8889. The controller serves its API at /v1/* and we expect a response (even if it's a 404 for `/health`, the TCP connection succeeding proves the server is up). We use `GET /v1/sandboxes` as the health indicator since that's a valid endpoint.\n- **Type:** http\n- **Input:** GET /v1/sandboxes\n- **Expected:** Returns 200 OK with a JSON array (likely empty `[]` since no sandboxes are created)\n- **Timeout:** 60 seconds (includes container startup + Rust binary init)\n\n### Scenario 2: list-snapshots\n- **Description:** Verify the snapshots listing endpoint responds correctly when no snapshots are available.\n- **Type:** http\n- **Input:** GET /v1/snapshots\n- **Expected:** Returns 200 OK with a JSON array (empty `[]`)\n- **Timeout:** 15 seconds\n\n### Scenario 3: invalid-sandbox-request\n- **Description:** Attempt to GET a non-existent sandbox to verify error handling.\n- **Type:** http\n- **Input:** GET /v1/sandboxes/nonexistent-id\n- **Expected:** Returns 404 with a JSON error body\n- **Timeout:** 15 seconds\n\n### Scenario 4: create-sandbox-no-kvm\n- **Description:** Attempt to create a sandbox via POST.
